# GenDesk 生图投单

把提示词 + 参考图写成一份**工单目录**丢进 GenDesk 的收件目录。GenDesk 会在 2 秒内
自动导入提示词与参考图、建批次、开始生成。

**你不生成图片，也不碰 GenDesk 的库。** 你只写文件。导入、编号发放、建批、调度、
重试、验收全在 GenDesk 里——那些不是智能任务，而且业务真相只能有一处。

> 写新的 `prompts-*` skill 时，不要引用本 skill，直接把同目录下
> `标准产出规范.md` 的「最后一步」抄进那个 skill 的收尾。少一次跳转就少一次遗漏。

## 什么时候用

用户在同一轮里给了参考图（`@` 引用或拖入文件）并要你写生图提示词。提示词写完就该投单——
而不是把文档交给用户、让他再去软件里手动导入两次。

## 一个条目 = 一条词 = 一个任务 = 一张图

这是新格式的全部形状。**条目名 `name` 就是那张图未来的文件名主干**：

```
W-王一博-55-正面   →   W-王一博-55-正面-hu72.jpg
└──── 你给的 ────┘      └── 你给的 ──┘└GenDesk 验收时发的 UID┘
```

GenDesk **一个字符都不会改** `name`。它必须能直接当文件名用（不含 `/`、`:` 等）。

## 四步

```bash
JOB=~/GenDesk交接/生图/收件/投单-$(date +%y%m%d-%H%M)
mkdir -p "$JOB/refs" "$JOB/prompts"
cp <参考图原路径> "$JOB/refs/"        # 拷贝，别移动别软链
```

2. Write `$JOB/工单.json` + 每个条目一份 `$JOB/prompts/<name>.txt`（格式见下）
3. 可选：Write `$JOB/说明.md`（方向地图/可替换变量表，给人看的）
4. **最后**：

```bash
printf ok > "$JOB/READY.txt"
pgrep -x gendesk >/dev/null || open -a GenDesk
sleep 3; cat "$JOB"/{结果,待确认,错误}.txt 2>/dev/null || true
```

把回执内容念给用户听（建了哪个批次、多少张、实际发出去哪些参数）。

**`READY.txt` 必须最后写**：没有它的目录 GenDesk 一律不碰，否则可能在图还没拷完时就开始导入。

**进程检测必须用 `pgrep -x`**：`-f` 会匹配到路径里带 "GenDesk" 的 node/vite 进程，
在开发机上「看起来能用」其实一直在说谎。

## 工单.json

```json
{
  "version": 1,
  "purpose": "i2v",
  "note": "王一博-卡套-买家秀",
  "defaults": { "ratio": "9:16", "size": "1152x2048", "format": "jpeg" },
  "items": [
    {
      "name": "W-王一博-55-正面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-正面.jpg"
    },
    {
      "name": "W-王一博-55-侧面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-侧面.jpg",
      "ratio": "3:4",
      "size": "1536x2048"
    }
  ]
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `version` | 是 | 恒为 `1`。别的值一律拒单（不认识的版本按 1 读会得到「看起来成功了的错误结果」）。 |
| `items[].name` | 是 | 语义名，**单内唯一**、可直接当文件名。等于 `prompts/<name>.txt` 的文件名。 |
| `items[].sku` | 是 | SKU 数字缩写（`55`）。交付时按 `style`+`sku` 分子目录。 |
| `items[].style` | 是 | 风格 / 人物（`王一博`）。 |
| `items[].ref` | 是 | 工单目录内的相对路径。**每条必填，GenDesk 不猜。** 多条可以共用一张图。 |
| `purpose` | 否 | 整单级。`i2v`（= 图生视频）或省略。验收通过的图会自动进视频流水线待发队列。 |
| `note` | 否 | 这一单的名字，会成为批次名，验收页按它分节。缺省用目录名。 |
| `defaults` | 否 | `ratio` / `size` / `format`，条目没写时用它。 |
| `skill` | 否 | 写出这批词的 skill 名，落到 `prompts.skill`，事后回查用。 |

正文一条一文件：`prompts/W-王一博-55-正面.txt`，内容是**纯正文，零元信息**。
正文里出现「比例：3:4 的竖构图」这种句子完全没问题——不会被当成参数吃掉。

## 四个坑

1. **正文里写「9:16」对模型不构成约束**——那是描述不是参数，要写进 `工单.json`。
2. **`ratio` 和 `size` 两个都要给**。实测（key `aixoras` · `gpt-image-2-1k`）：只发
   `ratio: 9:16` 回来的整批是 **1024×1024 正方形**；补上 `size` 才是竖幅。
   边长须为 16 的倍数（`1080x1920` 会被整批拒，1080 不是）。取值表：
   `1:1`→`1024x1024` · `3:4`→`1536x2048` · `4:3`→`2048x1536` ·
   `2:3`→`1024x1536` · `9:16`→`1152x2048` · `16:9`→`2048x1152`。
   只给 `ratio` 时 GenDesk 会补上配套 `size`，但**自己写清楚更好**。
   上游只按比例出图、分辨率它自己定（9:16 实测回来 941×1672），要精确像素得事后缩放。
3. **`prompts/` 与 `items` 必须一一对应**：多一个少一个都拒单。多出来的那份要么是
   漏写了 `items` 条目，要么是上一版的残留——两种都意味着这份工单和你以为的不一样。
4. **各条目画幅可以不同，仍然只建一个批次**（参数跟着任务走）。这是正确行为。

任务数 = 条目数。没有抽卡、没有笛卡尔积。

## 超阈值 / 失败

超过设置里的上限（默认 100 张）→ GenDesk **什么都不导入**，写一份 `待确认.txt`。
把里面的数字念给用户，问要不要跑；**不要自作主张创建 `确认.txt`**——阈值存在的意义
就是让人看一眼。用户同意后 `touch "$JOB/确认.txt"` 即可，或让他在设置页点「确认开跑」。

失败 → 工单留在原地 + `错误.txt`。校验阶段失败时库里一个字节都没变；若已经导入了一部分，
`错误.txt` 会**如实写明导入到哪一步**——照着它处理完再重试，否则会拿到第二份提示词。

## 边界

- 不要用 `osascript` 去点 GenDesk 界面，不要直接读写它的 SQLite。
- 不要替用户决定要不要花钱跑一批。
- 验收在 GenDesk 的验收页人工完成，这一步不该被自动化。
