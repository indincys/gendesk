# 提示词 skill 标准产出规范

给所有 `prompts-*` 系列 skill 用。**照抄「最后一步」那一节即可**，不必理解 GenDesk 的内部。

一句话：**别再把提示词写到桌面然后另找人投单——直接写进投单目录，最后 `touch READY.txt`。**
产出文档这个动作本身就是投单，中间没有第二个动作。

---

## 命名约定

| 位置 | 规则 | 例 |
| --- | --- | --- |
| skill 目录名 | `prompts-<题材>`（小写英文，产物类别做前缀） | `prompts-ugc-real` |
| `description` | **中文**，首句说清「产出什么」 | `为卡套产品实拍图批量创作真实生活场景…` |

前缀不是为了整齐：`prompts-` 开头的**必然**走 GenDesk 生图链路，`copy-` 开头的必然不走。
这条区分下游会直接用上。

小写而非 `Prompts-`：macOS 文件系统默认大小写不敏感、Linux 敏感，混用会在同步/入 git 时
变成两个东西。

---

## 一个条目 = 一条词 = 一个任务 = 一张图

这是整份规范的形状。**条目名 `name` 就是那张图未来的文件名主干**：

```
W-王一博-55-正面   →   W-王一博-55-正面-hu72.jpg
└──── 你给的 ────┘      └── 你给的 ──┘└GenDesk 验收时发的 UID┘
```

`W-王一博-55-正面` 里那个 `55` 是 **SKU 数字缩写**，由你给定；它不是批次号也不是序号，
GenDesk **一个字符都不会改**。UID 只在验收通过那一刻发放，生成中间产物没有号。

下游软件（`自动发布`）永远读交付目录里的 manifest，**不解析文件名**；文件名只是人工
核对的双保险。所以名字取得好不好只影响人读，不影响机器。

---

## 最后一步（照抄）

写完提示词后做四件事，**顺序不能变**：

```bash
JOB=~/GenDesk交接/生图/收件/投单-$(date +%y%m%d-%H%M)
mkdir -p "$JOB/refs" "$JOB/prompts"
cp <每张参考图的原路径> "$JOB/refs/"
#  ↑ 拷贝，不要移动也不要软链：工单目录成功后会被移进 _已收录/，软链会断
```

然后用 Write 写：

- `$JOB/工单.json`（格式见下）
- 每个条目一份 `$JOB/prompts/<name>.txt`（**纯正文，零元信息**）
- 可选 `$JOB/说明.md`（方向地图、可替换变量表这类给人看的东西）

**最后**：

```bash
printf ok > "$JOB/READY.txt"
pgrep -x gendesk >/dev/null || open -a GenDesk
sleep 3; cat "$JOB"/{结果,待确认,错误}.txt 2>/dev/null || true
```

三行分别是：宣告就绪 · 没开就拉起来 · 回读结果告诉用户。

> **进程检测别用 `pgrep -f GenDesk`**。`-f` 匹配整条命令行，而仓库路径里带 "GenDesk" 的
> node/vite 进程会全部命中——它会在开发机上「看起来能用」，其实一直在说谎。用 `-x`（精确匹配进程名）。

`READY.txt` 必须最后写：没有它的目录 GenDesk 一律不碰，否则它可能在图还没拷完时就开始导入。

## `工单.json` 格式

```json
{
  "version": 1,
  "purpose": "i2v",
  "note": "王一博-卡套-买家秀",
  "skill": "prompts-ugc-real",
  "defaults": { "ratio": "9:16", "size": "1152x2048", "format": "jpeg" },
  "items": [
    {
      "name": "W-王一博-55-正面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-正面.jpg"
    },
    {
      "name": "W-王一博-55-侧面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-侧面.jpg",
      "ratio": "3:4",
      "size": "1536x2048"
    }
  ]
}
```

### 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `version` | 是 | 恒为 `1`。别的值一律拒单 |
| `items[].name` | 是 | 语义名，**单内唯一**、可直接当文件名（不含 `/` `:` 等）。等于 `prompts/<name>.txt` 的文件名 |
| `items[].sku` | 是 | SKU 数字缩写（`55`）。交付时按 `style`+`sku` 分子目录 |
| `items[].style` | 是 | 风格 / 人物（`王一博`） |
| `items[].ref` | 是 | 工单目录内相对路径。**每条必填**。多条可以共用一张图（只会入库一次） |
| `items[].ratio/size/format` | 否 | 条目级参数，覆盖 `defaults` |
| `purpose` | 否 | **整单级**。`i2v`（= `图生视频`）或省略。写别的值整单被拒 |
| `note` | 否 | 这一单的名字 → 批次名 → 验收页分节标题。缺省用目录名 |
| `defaults` | 否 | `ratio` / `size` / `format`，条目没写时用它 |
| `skill` | 否 | 写出这批词的 skill 名，落到 `prompts.skill`，事后回查「这批词是谁写的」 |
| `jobId` | 否 | 去重键，缺省取目录名。**必须全局唯一** |

### 正文文件

`prompts/<name>.txt`，内容是**纯正文，零元信息**。

这是新格式相对旧格式（`提示词.txt` + 组头键）最重要的改进：正文里出现
「比例：3:4 的竖构图，人物居中」这种句子完全没问题——它不会被当成参数吃掉。
旧格式里那条提示词会当场少一句，而且不报错。

`prompts/` 与 `items` **必须一一对应**，多一个少一个都拒单。多出来的那份要么是
漏写了 `items` 条目，要么是上一版的残留——两种都意味着这份工单和你以为的不一样，
而少跑一张图是不报错的失败。

## 画幅：`ratio` 与 `size` 两个都写

实测（key `aixoras` · 模型 `gpt-image-2-1k`，三个批次 56 张）：

| 发出去的参数 | 回来的图 |
| --- | --- |
| `aspectRatio: 9:16` 单独发 | **1024×1024 正方形**（比例参数没起作用） |
| `aspectRatio: 9:16` + `size: 1088*1920` | 941×1672（≈9:16，竖幅成立） |
| `size: 1080x1920` 单独发 | **整批 400**：`edges must be multiples of 16` |

所以：**`size` 是这条链路上真正决定画幅的那个参数**，`ratio` 一起写是为了换 key /
换模型时不至于翻车。这两个结论都只对上面那把 key 成立，但代价不对等——多写一行是零成本，
少写一行是一整批正方形。

只写 `ratio` 时 GenDesk 会替你补上配套 `size`（那是**补一个缺失字段**，不是改你写下的
取值）；但自己写清楚更好——补出来的值将来可能随取值表变。

**能用的取值**（同时满足「正好是该比例」和「两边都是 16 的倍数」）：

| 比例 | 尺寸 | | 比例 | 尺寸 |
| --- | --- | --- | --- | --- |
| `1:1` | `1024x1024` | | `3:4` | `1536x2048` |
| `4:3` | `2048x1536` | | `2:3` | `1024x1536` |
| `9:16` | `1152x2048` | | `16:9` | `2048x1152` |

**竖版 1080p 写不出来**：1080 ÷ 16 = 67.5，`1080x1920` 会被端点整批拒。精确 9:16 且
两边都是 16 倍数的取值只有 …/1008×1792/**1152×2048**/1296×2304… 这一列，1152×2048 是
跨过 1080×1920 的那一档。（`1088x1920` 边长合法，但它是 17:30 不是精确 9:16。）

**写下的像素不等于拿到的像素**：上游只按比例出图、分辨率它自己定（实测 9:16 回来的是
941×1672，约 1.57MP）。要正好 1080×1920 得验收之后自己缩放。

## 三个必须知道的坑

**① 提示词正文里写「9:16」对模型不构成约束。** 那是描述不是参数。要竖幅就在
`工单.json` 里写 `ratio` + `size`。

**② 各条目画幅不同也只建一个批次。** 参数跟着**任务**走，不再决定切分：
一次工单 = 一个 run。你写一份工单、三个条目三种比例，GenDesk 建**一个**批次，
每条任务拿自己那一份参数。验收页按投单分节，读起来就是你投的那一单。

**③ 任务数 = 条目数。** 没有抽卡、没有笛卡尔积。想要同一条词的第二张，就多写一个条目
（它需要自己的 `name`，因为名字就是文件名）。

---

## 挂靠：每个条目都必须点名

GenDesk **不会按顺序猜**哪张图配哪条词。猜错的代价是整批图配错提示词，
而那要到验收时才看得出来——那时钱已经花完了。

所以 `items[].ref` 是必填的，没有「单条目时可省」这种特例。

---

## 参考图必须有本地路径

用户 `@` 引用或从访达拖入的文件有路径，可以直接 `cp`。
**纯粹粘贴进对话的图片没有路径**——那种情况请用户先把图存到某个目录再给路径，
不要编一个路径出来。

---

## 超阈值会怎样

单份工单超过设置里的上限（默认 **100 张**）时，GenDesk **什么都不导入**，
在工单目录写一份 `待确认.txt` 并等人表态。此时提示词、参考图一条都没进库。

确认有两个口子，做的是同一件事：

- 在工单目录里建空文件 `确认.txt`
- 或在 GenDesk 设置页「Claude Code 收件」点「确认开跑」

skill 读到 `待确认.txt` 时，把里面的数字念给用户听，问一句要不要跑，
**不要自作主张 touch `确认.txt`**——阈值存在的意义就是让人看一眼。

---

## 失败了怎么办

校验发生在写库之前，所以校验阶段失败时库里一个字节都没变。失败时工单目录**留在原地**，
里面多一个 `错误.txt` 写着原因。最常见的几种：

- `size` 边长不是 16 的倍数
- 某个条目没写 `ref`，或 `ref` 指向的文件不在包内
- `prompts/` 与 `items` 数量对不上
- `name` 不能直接当文件名（含 `/`、为空）
- `sku` 或 `style` 空着
- `purpose` 写了 `i2v` / `图生视频` 以外的词
- `version` 不是 1

若已经导入了一部分（参考图落盘、提示词进库之后才出的错），`错误.txt` 会**如实写明
导入到哪一步**。照着它处理完再重试——否则会拿到第二份提示词和第二个批次，花两份钱。

改好后让用户在设置页点「重试」，或换一个工单目录名重投。

---

## 边界

- **不要**用 `open`/`osascript` 去点 GenDesk 的界面，也不要直接读写它的 SQLite。
- **不要**替用户决定要不要花钱跑一批——投单即开跑（阈值内）。
- 验收在 GenDesk 的验收页人工完成，这一步不会、也不该被自动化。
