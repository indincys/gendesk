# 内部图片生产工具 V1 设计输入技术摘要

> 本文档摘自 `内部图片生产工具_V1技术选型定稿.md`，只保留与**原型设计判断**直接相关的部分。
> 完整技术文档是开发实现阶段的基准，与本次设计任务无关的后端实现、部署、CI/CD 等内容已剔除。

## 0. 任务定位说明

你现在的任务是**原型设计（视觉与交互判断）**，不是代码实现。下面列出的技术约束是为了让设计能够被真实落地，不是要你参与工程决策，也不需要遵守开发流程规范（测试、CI 门禁等与你无关）。

配套阅读：`内部图片生产工具_V1需求文档.md`，功能范围与业务规则的权威来源，本摘要不重复其内容。

## 1. 已拍板的视觉方向决策（约束，不是讨论项）

以下是用户已确认的决策，设计时直接作为前提，不需要重新论证或提供备选：

- **浅色优先**的整体基调。
- 视觉要求：**冷静、快速、高级、目标明确、信息密度高但有呼吸感**。主工作区优先，导航和辅助区域视觉后退，界面要有颜值但不嘈杂。
- 强调色采用 **低饱和蓝色**，可参考 Linear 的克制蓝，并保留 Things 3 的轻盈感，用于主操作、选中态、进度和引导高亮。
- 组件方案从 Ant Design 调整为 Tailwind CSS + shadcn/ui + Motion，目的是获得**完全的视觉控制权**，即设计不受组件库默认样式限制，可以做高保真、有辨识度的界面，而不是通用后台管理系统的观感。

### UI/UX 审美方向（风格约束）

参考 Linear 官方设计理念。整体是跨 macOS 和 Windows 的图片生成生产力工具：浅色优先，冷静、快速、专业，主工作区承载提示词、参考图、任务和验收结果，导航、筛选、状态条等辅助区域降低对比度，只在异常和关键动作时提高权重。

视觉丰富度来自精密对齐、紧凑头部、清晰层级、柔和分隔线、细腻圆角边框、中性耐看的界面表面、低饱和蓝色强调、多层级景深、柔和阴影和轻微环境光。图片墙和缩略图区域可以更有表现力，但不要让装饰抢走内容。

禁止通用 AI 模板风：不要大面积紫蓝渐变、发光球、玻璃拟态、营销页 hero、巨大漂浮卡片、赛博风背景，也不要为了高级感牺牲信息密度。动效只服务于选择、进度、悬停、拖拽和状态变化。

## 2. 前端技术基座（设计必须能被这套体系承接）

| 组件  | 选型                            | 对设计的含义                                                                  |
| --- | ----------------------------- | ----------------------------------------------------------------------- |
| 组件库 | shadcn/ui（Radix UI 原语，源码进仓库）  | 基础组件（Button/Dialog/Table/Toast 等）以此为基座定制，设计可以深度改造样式，但交互行为应符合这些组件的可访问性模式 |
| 样式  | Tailwind CSS 4，CSS 变量 token 化 | 设计交付的颜色、圆角、间距需要能提炼为一套 token（变量），而不是零散的具体数值                              |
| 动效  | Motion（framer-motion 后继）      | 交互动效是一等能力，可以设计进入/退出、状态过渡、选择反馈、进度反馈和列表更新的轻微动效                            |
| 表格  | TanStack Table（headless，自绘视觉） | 任务列表等复杂表格的视觉完全自由，不受表格组件默认样式限制                                           |
| 图标  | lucide-react                  | 图标风格已定为 lucide 这一套线性图标，设计时基于此图标语言                                       |

## 3. 数据更新机制对交互设计的影响

- 任务进度**不是轮询**，而是后端主动推送事件（`task://progress`、`task://status-changed`、`batch://summary`、`update://state`），**按 250ms 节流合并**。
- 对设计的含义：进度类 UI（进度条、状态徽章、批次汇总）可以设计为**近实时但非逐帧**的更新节奏，动效可以围绕"离散更新点"设计（比如每次更新有一个轻微的过渡动画），不需要按连续轮询的思路做。

---

## 4. 大批量场景对信息密度的影响

- 单次批量规模 1 到 500 张，任务列表和素材/作品图片墙**全部走虚拟滚动**（只渲染可视区域）。
- 列表中只加载**缩略图**（长边 512px），原图仅在大图审阅时按需加载。
- 对设计的含义：需要设计一套在 500 行/张规模下依然清晰可扫视的密度方案，比如任务列表的**固定行高**、图片墙的卡片尺寸和信息层级，要在"信息量大"和"不拥挤"之间做取舍。

---

## 5. 主题与设计交付格式要求

- 主题基调：浅色优先。
- 颜色、圆角、间距全部通过 **CSS 变量 + Tailwind token** 承载，为设计落地留自由度。
- 动效需要考虑 `prefers-reduced-motion` 的降级方案（无障碍要求）。
- 画布与响应式方案需要同时兼容 **MacBook Pro** 和 **Windows 系统 4K 显示器**使用场景，核心操作区不能依赖单一屏幕比例。
- **设计交付物需要具体到 token 级别**（色值、圆角值、间距值、字号阶梯等），因为这份设计产出最终会原样喂给开发阶段去实现，不是抽象的风格描述。

## 6. 核心设计对象一：任务状态（8 态）

任务列表需要清晰区分以下状态，这是原型设计的核心内容之一：

- 待生成
- 生成中
- 重试中
- 成功
- 失败
- 待验收
- 已通过
- 未通过（进入废纸篓）

默认状态逻辑：**成功即待验收**。界面可用 **5 个视觉组承载 8 态**，例如：

- 待处理：待生成
- 生成中：生成中、重试中
- 异常：失败
- 待验收：成功、待验收
- 验收结果：已通过、未通过

任务列表每一行还需要展示：当前状态、使用的参考图、提示词分组和编号、使用的 API Key 标识、生成进度、失败原因、重试次数。

API Key 监控的默认方案：**任务页顶部提供可展开状态条**，默认低对比、紧凑、可折叠，用于快速看到当前 Key 健康情况；异常时提高视觉权重，完整 Key 管理放在设置页。

## 7. 核心设计对象二：错误类型与提示文案基调

| 错误类型          | 触发场景            | 用户侧应感知到的信息                           |
| ------------- | --------------- | ------------------------------------ |
| Timeout       | 连接/读取超时         | 会自动重试并换 Key，通常不需要用户介入                |
| RateLimited   | 接口限流（429）       | 会退避后自动重试，可提示"正在排队重试"                 |
| ContentPolicy | 提示词违规           | 重试一次仍失败则标注"违规"，需要用户能一眼看出这是内容问题而非系统故障 |
| Auth          | Key 失效（401/403） | 不会自动重试，需要醒目提示"建议停用该 Key"             |
| Interrupted   | 软件中断后恢复         | 需要提示"因中断请重试"，且不应让用户误以为任务已丢失          |
| Other         | 其余情况            | 按用户设置的重试次数处理                         |

这张表的意义：**不同错误需要不同的视觉严重程度和文案基调**，比如 Auth 类错误应该比 Timeout 类错误更醒目，因为前者需要用户主动处理。

## 8. 核心设计对象三：作品/任务可展示字段

以下是每条任务/作品记录中，**面向界面展示**的信息（不是数据库字段定义，只提炼展示层需要覆盖的信息点）：

- 任务：状态、参考图缩略图、提示词分组+编号、使用的 API Key、生成进度、错误原因、重试次数、结果图片
- 通过验收的作品：图片、对应提示词原文、所属分组/标签/编号、验收时间、是否收藏
- 提示词分组卡片：分组名称、标签、场景分类、提示词数量（提示词原文不作为卡片主视觉，仅作为详情信息）

提示词原文通常较长，平均每条至少约 **500 字**。软件内所有需要展示提示词的地方，都必须提供舒展、可阅读的展示方式（例如足够宽高的详情弹窗或独立详情区），不能把 500 字提示词挤在很小窗口里，也不能依赖用户手动拖拽窗口才能看完整内容。

## 9. 图片生成页的交互结构

本轮反馈明确放弃“参考图在生成页占据巨大空间”的布局。图片生成页改为：

- **提示词模块在上，参考图模块在下**。
- 未选择提示词组/未导入临时提示词时，提示词模块需要提供明确的“选择提示词组”或“导入提示词”引导。
- 未选择/未上传参考图时，参考图模块需要提供明确的“选择参考图”或“上传参考图”引导。

参考图在生成页上的存在形式应是**已选择结果区**，不是大型素材浏览区。选择参考图时打开弹窗，在弹窗内展示参考图库图片；用户选中的参考图再进入生成页的参考图结果区。

选择提示词分组时打开弹窗查看该分组下的提示词。如果当前没有导入临时提示词，点击“选择提示词分组”应进入提示词库选择现有分组，而不是把提示词库所有分组全部铺在图片生成页上。如果已经在图片生成页导入了提示词，则导入的提示词直接在生成页按分组展示。

不同参考图允许使用同一组提示词，并各自独立生成图片。交互上必须清晰引导“提示词组”和“参考图”的对应关系：上传/选择参考图后，每个参考图都要明确挂靠到某个提示词组；当选择了多组提示词和多张参考图时，应通过低饱和蓝色、细边框、轻微背景层级和短促微动效引导用户逐一建立对应关系。只有所有提示词组与参考图都建立对应关系后，才允许点击“开始生成”。

## 10. 验收、废纸篓与作品库

验收页默认采用**网格总览 + 大图逐张模式 + 键盘快捷键**：

- 网格视图支持批量快速验收，可自定义网格大小/每行数量。
- 网格视图支持多选图片，快速粗略选出不合适结果并直接移至废纸篓。
- 剩余图片通过原图/大图逐张查看，逐一验收。

废纸篓内容保留**缩略图 + 提示词**，清理后彻底删除。

作品库允许逐一点开查看详情，详情内需要能查看图片细节、对应提示词及相关信息。

---

## 11. 提示词库与参考图库

提示词库不要设计成“点击三次才能看到提示词原文”。默认每个分组展开，按提示词编号和摘要级信息陈列；点击编号即可打开弹窗查看具体提示词。展开状态需要保持低噪音和可扫视，长提示词原文进入详情弹窗，不直接铺满列表。

参考图库需要和提示词库使用一致的分组体系，但参考图库使用网格展开。参考图库内的图片允许查看大图、编辑，包括更换图片、编辑分组、删除该参考图等。

---

## 12. 原型范围与待设计方自定项

首轮原型范围：**所有页一次性完整输出**。建议覆盖图片生成、任务状态/队列、验收、废纸篓、提示词库、参考图库、作品库、设置/API Key 管理。

以下项由设计方基于信息架构自行拍板，不需要再向用户追问：批次层级、导航结构、中断恢复 UI。
