# 作品目录整理

GenDesk 是通用生成工具。作品归属由用户或调用方给定，不从图片名猜产品，不绑定任何具体产品项目。

## 目录

在设置的「作品目录与归档」中指定根目录。本机选择 `/Users/indincys/Workspace/软件开发/GenDesk`，与 `代码/` 分开。

```text
<作品根>/
├── _草稿/生成图片/<产品>/<款式>/<需求>/
└── 成品/
    ├── 生成图片/<产品>/<款式>/<需求>/
    └── 生成视频/<产品>/<款式>/<需求>/
```

产品、款式可以省略；未知需求明确放入 `需求待补充`。同一归属跨多次生成、审稿、视频尝试持续归入同一目录。日期只在文件名，来源只在元数据，运行批次不参与目录身份。

文件名使用 `YYYY-MM-DD_内容名称_稳定身份.扩展名`。图片身份为既有 UID，视频为 clip ID 和尝试次数，防止覆盖。原始完整语义名保存在数据库；过长或包含符号的目录名安全处理并防止清洗碰撞。

人工生成在确认卡填写产品、款式、需求。外部工单或 CLI 使用 `organization`：

```json
{
  "organization": {
    "product": "陶瓷水杯",
    "style": "奶油白款",
    "requirement": "厨房场景图",
    "source": "小红书晒单需求"
  }
}
```

可写在工单顶层或条目上，条目整对象覆盖顶层。没有 SKU 的非商品任务可以只提供 organization 和参考图、正文。重复生成时沿用相同名称；jobId 仍负责投单去重，不用它充当需求名。CLI 单条支持 `--product --style --requirement --source`，显式归属必须由连接快照声明 `content-organization`，旧应用不能静默吞掉。

任务快照保存归属，审稿时永久写入作品，视频入队时再独立快照；提示词、运行批次或父图删除后仍保留归属。Poster 接入仍默认关闭，开启后逐次确认；它直接引用成品，不额外制造验收批次图片副本。

## 内部数据

数据库、密钥、参考图副本、缩略图、操作记录和恢复快照保存在系统应用数据目录，不在 `.app` 包内，也不在代码仓库内。图片通过后草稿移出用户草稿目录，恢复快照留在应用数据区；视频内部快照用于撤销、重新交付。这些内部文件不是用户浏览成品的入口。

旧的 `GenDesk交付/交付-短日期-运行编号/` 和 `outputs/视频/分组/` 停止作为新作品出口。旧 `delivery`、`clipsOutputDir`、`PosterSettings.libraryRoot` 仅为兼容旧数据保留，不再决定新成品落点。

## 既有文件整理

应用不会在启动时擅自搬文件。退出对应 GenDesk 后，使用应用可执行文件的离线维护命令：

```text
gendesk organize-library --database <运行库> --root <作品根> --assignments <归属JSON> --report <报告JSON> [--poster-bin <Poster可执行文件>] [--apply]
```

这是应用可执行文件的维护命令，与 `~/.local/bin/gendesk` 投单客户端不同。无 `--apply` 时只在副本中计算预览，不迁移原库、不移动原文件。`--apply` 检查目标库未被其他进程打开、没有在途任务，再备份运行库、校验拷贝、通过 Poster 通用接口重绑原有图片路径，最后提交 GenDesk 引用和完整根目录设置。不会重跑生成，也不改变审稿结果和作品身份。

归属 JSON 结构为 `{"tasks":{"任务ID":{...organization}},"works":{"作品ID":{...organization}}}`；用于本次存量整理，不把具体产品规则写进软件。不存在 live work 的旧 Poster 记录保持原路径，不新建、不复活；因此清理旧出口前还须核对它们是否仍被引用。

Poster 必须声明 `same-identity-path-relink` 能力。同来源身份、商品 ID 和图片内容保持一致，只改永久路径；预检必须全部是已存在或已删除图片。任一步失败都保留原文件，修复后可重试。核对数据库完整性、所有新路径内容哈希、原有 Poster 图片数量和归属后，才把不再被引用的旧出口移到 `_归档/`。
