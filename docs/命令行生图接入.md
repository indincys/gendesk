# GenDesk 命令行生图接入

适用版本：CLI / 应用 0.37.0，控制协议 2，清单 `version: 1`。本文是外部 Agent 接入 GenDesk 的唯一完整规范；README、AGENTS 和 skill 只保留入口与执行边界。写提示词不等于授权生图，只有用户要求生成或已有生成授权时才 submit。

GenDesk 接收 **UTF-8 正文文件 + 本地参考图 + 显式配对清单**。Agent 只通过 `gendesk` 命令与应用交互：CLI 把清单打包后经本机控制通道（`127.0.0.1` + 每次启动的随机令牌）通知应用收录，应用**不监听、不扫描任何目录**。API Key、模型选择、收录、生成调度、重试、人工验收和成品交付由应用管理；外部工具不直接写 SQLite。

## 1. 安装与连接

前置 Node.js ≥ 22。本机命令在 `~/.local/bin/gendesk`；macOS/Unix 从仓库安装或更新：

```bash
pnpm --dir /Users/indincys/Workspace/软件开发/GenDesk/代码 install:cli
gendesk --version
gendesk doctor
```

安装器核对 CLI、package.json 与应用配置版本，验证后原子替换 `~/.local/bin/gendesk` 入口与同目录的 `gendesk.mjs`（两文件保持同一目录）。安装不改应用设置、不投单。应用升级不会自动更新这份独立 CLI，升级后须重新安装。仓库内也可 `pnpm gendesk`，Windows 用 `node scripts/gendesk.mjs`。

应用每次启动写 `~/GenDesk交接/连接.json`（仅当前用户可读写）：`protocol`、`port`、`token`、`appPath`、`root`、`taskThreshold`、`features`。CLI 只认协议 2；旧版应用写的连接文件直接报错（退出码 8），请更新并重启应用。

- `--version`：`cliVersion`、`protocol`、`orderVersion`，不需要应用。
- `doctor`：读连接文件并发 `hello`，返回 `status: online/offline` 与应用能力；不启动应用、不写文件。
- `submit`、`confirm`、`retry`、`v2v …`：GenDesk 未运行时在 macOS 上以 `--background` 后台启动（不弹窗、不抢焦点），等新连接文件出现后继续；其他系统请先自行启动。`GENDESK_APP` 可指定应用包，`GENDESK_LAUNCH=0` 关闭自动启动。
- `status`、`overview`：应用未运行时返回退出码 8，不启动应用。

交接根固定为 `~/GenDesk交接`，没有 `--root`。工单包落在 `~/GenDesk交接/生图/收件/<jobId>/`，收录后应用移档到 `生图/_已收录/`。

## 2. 正文与参考图

- 一份非空 UTF-8 TXT = 一条提示词 = 一个任务 = 一张图。中文、英文、多段文字均可；不按段落、序号或 `====` 拆分。
- TXT 只放发给模型的正文，不放文件路径说明、SKU、写作分析或 Markdown 代码围栏。CLI 按原字节复制，Rust 收录时去掉首尾空白，正文中的“比例：3:4”不会被解析成参数。
- 接收层没有额外设定提示词字数上限；远端模型仍可能有自己的限制。没有单独的 negativePrompt、seed、n、model 或 API Key 输入字段，不自创参数。
- 参考图必须是存在、非空、可解码的本地文件；常规使用 JPG/PNG。URL、Base64 或对话里的图片标记不能代替文件路径；附件若有可访问路径即可使用，没有路径先取得实际文件，不编造路径。
- 单图用 `ref`；多图用 `refs` 有序数组，二选一。每项 1～16 张，不重复引用相同内容。多个条目可以共用参考图，CLI 按内容打包复用。
- 数组首张是 Image 1（主参考），第二张是 Image 2，依次类推。正文应说明各图角色；不要拼接触表、丢掉环境参考或依赖上一次请求记忆。多个附件不展开成多个任务。
- 参考图不用匹配输出尺寸，也不要求边长为 16 的倍数。应用对长边超过 2048 或文件超过 3 MiB 的参考图会尝试制作上传压缩副本；这不是接收文件大小上限，也不保证模型按原图像素读取。

## 3. 批量清单（推荐）

清单使用 UTF-8 JSON；相对路径以**清单所在目录**为基准，也支持绝对路径与 `~/`。显式配对每一条，不按两个目录的排序猜配对。以下示例需要将素材换成真实文件：

```json
{
  "version": 1,
  "note": "水杯厨房场景",
  "skill": "Codex场景提示词",
  "organization": {
    "product": "陶瓷水杯",
    "style": "奶油白款",
    "requirement": "厨房场景图",
    "source": "小红书晒单需求"
  },
  "defaults": { "ratio": "3:4", "format": "jpeg", "quality": "high" },
  "items": [
    {
      "name": "水杯晨光桌面",
      "promptFile": "提示词正文/水杯晨光.txt",
      "refs": ["商品实拍/水杯正面.jpg", "场景参考/厨房桌面.jpg"]
    },
    {
      "name": "水杯窗边竖幅",
      "promptFile": "提示词正文/水杯窗边.txt",
      "ref": "商品实拍/水杯正面.jpg",
      "ratio": "9:16"
    }
  ]
}
```

| 位置 | 字段与约束 |
| --- | --- |
| 顶层 | `version` 建议显式为数字 1，CLI 省略时补 1；非空 `items` 必填 |
| 顶层可选 | `jobId`、`note`、`skill`、`purpose`、`defaults`、`organization` |
| 每个条目必填 | `name`、`promptFile`、`ref` 或 `refs` |
| 每个条目可选 | `organization`、`sku`、`style`，以及生成参数表里的各字段 |
| 字符串 | 路径、名字、SKU、归属、参数文本都用字符串；例如 SKU 写 `"55"` 而非数字 55 |
| `purpose` | 整单级；普通生图省略，验收图确实用于后续转视频时写 `i2v` |

CLI 严格拒绝未知字段。对外统一使用本文中的字段名；不要把 Rust 内部快照字段（如 aspectRatio、referenceImageIds）放进 CLI 清单。

`name` 单内唯一，大小写及 Unicode 等价名字也不能重复；最长 180 个 UTF-8 字节，不得含控制字符或 `<>:"/\\|?*`，不得以点结尾或使用系统保留名。CLI 会去掉 name 首尾空白。它是语义名与工单内正文身份，不是最终文件路径；交付名按 `YYYY-MM-DD_内容名称_稳定身份.扩展名` 生成，目录和文件名会做安全规范化，原语义名保留在记录中，详见 [作品目录整理](作品目录整理.md)。

需要同一提示词的第二张图，增加一个不同 name 的条目；任务数始终等于条目数。

## 4. 内容归属

新任务推荐填写 `organization: {product, style, requirement, source}`。它决定按产品、款式、需求持续归档，来源只作追溯。产品、款式可留空，未知需求落到 `需求待补充`；应优先给用户能识别的固定需求名。同一需求续做沿用相同名称，不加入日期、续批、重做或随机编号；jobId 只管一次运行去重。

organization 可写顶层，也可写条目。**条目整对象覆盖顶层，不逐字段合并**；省略的归属属性在应用内按空字符串处理。产品、款式和需求非空时不得有首尾空白、路径或保留字符，最长各 180 UTF-8 字节；source 为追溯文本。没有 SKU 的任务只提供 organization，不编造商品编号。

不含 organization 的清单仍接受，条目 `sku`、`style` 必须是非空字符串，应用仅沿用明确字段作兼容归属，不从文件名猜产品。已有 Poster 商品映射需要 sku/style 时继续提供真实值，并与 organization 保持一致；organization.style 表示款式，不是任意视觉风格。作品根由应用设置决定，CLI 不指定或猜测成品目录。

## 5. 生成参数

参数可放在 defaults 或单条；**逐字段覆盖，未写的字段仍继承 defaults**。正文中描述比例、像素或“高清”不能代替参数。

| 字段 | 接收值 |
| --- | --- |
| `ratio` | `1:1`、`16:9`、`9:16`、`4:3`、`3:4`、`3:2`、`2:3`、`21:9` |
| `size` | `宽x高`（正整数，均为 16 的倍数），或 `auto` |
| `format` | `jpeg`、`png`；jpg 归一化为 jpeg；不接受 webp 作为输出格式 |
| `quality` | `auto`、`low`、`medium`、`high`、`xhigh`、`max`、`standard`、`hd`，缺省 high |
| `clearAiMetadata` | 布尔值，默认 true，本地输出处理开关 |
| `removeC2pa` | 布尔值，默认 true，本地输出处理开关 |

质量档位是否可用由远端模型决定；high 不是所有模型的最高档，此值与本地 JPEG 编码质量无关。CLI 接受的参数不等于所有模型都支持。

| 比例 | 缺少 size 时自动补的尺寸 |
| --- | --- |
| 1:1 | 1024x1024 |
| 3:4 | 1536x2048 |
| 4:3 | 2048x1536 |
| 2:3 | 1024x1536 |
| 3:2 | 1536x1024 |
| 9:16 | 1152x2048 |
| 16:9 | 2048x1152 |
| 21:9 | 2016x864 |

通常只填 ratio，让应用补配套 size；用户明确像素要求时再写 size，并自行保持比例一致。**defaults 同时写 ratio 和 size 时，条目改 ratio 必须一并更新 size，否则仍继承默认尺寸。** 当前后端不会拒绝比例与尺寸互相矛盾的组合，也不会替换你显式给定的 size。`1080x1920` 因 1080 不是 16 的倍数会拒单。请求尺寸不保证远端返回精确同像素，精确交付像素需验收后核对。

## 6. 命令与执行顺序

单条示例（产品、款式、需求和文件路径替换为实际值）：

```bash
gendesk validate --prompt /绝对路径/水杯晨光.txt --ref /绝对路径/水杯正面.jpg \
  --product 陶瓷水杯 --style 奶油白款 --requirement 厨房场景图 \
  --source 小红书晒单需求 --ratio 3:4 --format jpeg --quality high
gendesk submit --prompt /绝对路径/水杯晨光.txt --ref /绝对路径/水杯正面.jpg \
  --product 陶瓷水杯 --style 奶油白款 --requirement 厨房场景图 \
  --source 小红书晒单需求 --ratio 3:4 --format jpeg --quality high
```

`--name` 省略时取正文文件名主干。单条只支持一个 `--ref`，多参考图改用清单。单条使用 --product、--requirement 或 --source 任一参数才创建 organization；非商品单可只给 --requirement。不填这三者则走 --sku + --style 模式。`--manifest` 不能与单条输入参数混用，可以与 `--job-id` 共用。

批量执行：

```bash
gendesk validate --manifest /绝对路径/场景任务.json
gendesk submit --manifest /绝对路径/场景任务.json
gendesk status cli-返回的工单编号
gendesk overview
```

validate 先检查文件、UTF-8 正文编码、字段类型、名字与配对，再调用应用可执行文件的 `validate-intake` 只读入口，复用 Rust 收录解析、参数归一化、归属校验和实际图片解码，返回 `validation: full`。预检不启动 GUI、不打开数据库、不调用生图；应用关闭时也能用（取连接文件里的 `appPath`，或用 `GENDESK_APP_BIN` 指定）。归一化后的参数在 `preflight.items[].paramsJson / wireJson`，参考图尺寸和 SHA-256 在 `preflight.references`。收录时仍重新核对实际输入。

submit 依次：连上应用（必要时后台启动）→ 预检 → 复制正文与参考图到收件目录并校验，最后写 READY.txt → 经控制通道请求收录。**收录在这次调用里完成**：返回时已建批开跑（`ingested`）、停在待确认（`hold`）或失败（`error`），不需要轮询。生成与人工验收在 GenDesk 审图页进行；`overview` 可读各态任务数，判断是否跑完、是否该提醒人审稿。

给 Agent 的顺序：准备正文与清单 → validate → 在已有生成授权内 submit → 按返回的 status 处理 → 提醒用户在 GenDesk 审图。只写词时交付文件即可，不 submit。

## 7. 去重、状态与失败恢复

CLI 根据工单、正文和参考图内容生成稳定 jobId。同样输入重复调用复用原单，返回 `reused: true`，不会二次收录；同 ID 不同内容报错，不覆盖。确实要额外生成一次且已有授权时，显式给新的 `--job-id` 或清单 jobId。**失败或状态不明先 `gendesk status <原jobId>`，不自动换 ID 重投。**

| JSON 状态 | 含义 | 退出码 |
| --- | --- | --- |
| ingested | 已收录建批，不代表生成或验收完成 | 0 |
| ingesting | 正在导入（并发调用时可见） | 0 |
| hold | 超阈值待用户确认，尚未导入 | 4 |
| error | 收录失败，`job.message` 写明已导入到哪一步 | 5 |
| duplicate | ID 被台账占用，本次未收录 | 6 |
| not_found | 未找到这个 jobId | 7 |
| client_error | 输入或配置错误 | 2；应用不可用为 8，应用拒绝请求为 5 |

**待确认**：超过阈值（默认 100 张）的单停在 hold，什么都不导入。向用户说明张数与配对，取得明确同意后再 `gendesk confirm <jobId>`；已有生成授权不等于可以跳过这道确认，CLI 没有绕过开关。

**失败重试**：`gendesk retry <jobId>` 沿原身份检查点只补未完成步骤，保留已有提示词与参考图 ID，不会整单重新导入，重复调用或进程重启后也不会多建批次。已经导入过内容后，正文、归属、参数、参考图内容须保持一致；尚未导入任何业务记录的单可修正原包后重试。没有检查点的历史部分导入或 running 单会明确拒绝盲目重放。确实要改内容重新生成时，在用户授权下用新 jobId 新建任务。

## 8. 图生视频提示词改写

验收通过并转入图生视频的图，提示词改写由 Agent 完成，应用不提供交接目录：

```bash
gendesk v2v pending
gendesk v2v rewrite --file /绝对路径/改写结果.json
```

`pending` 按提示词组返回待改写条目（`id` 为 `W<作品号>`、缩略图路径、生图提示词全文与可变部分、本组改写说明）。改写结果文件可以是 JSON 数组、`{"lines": [...]}` 或每行一个 JSON，每条 `{"id": "W123", "videoPrompt": "…"}`，可选 `modelVersion`、`duration`、`videoResolution`；`id` 必须原样回传。写回后由应用提交即梦；Agent 不调用 dreamina。

## 9. 给提示词 Agent 的简短约定

> 按 GenDesk 0.37.0 接收契约交付：每张图一份 UTF-8 纯正文 TXT，另写 version=1 的 JSON 清单。逐项指定 name、promptFile 和 ref 或有序 refs；多图在正文说明 Image 1、Image 2 的用途。新任务填写 organization 的产品、款式、固定需求和来源，没有 SKU 不编造编号。ratio/size/format/quality 写参数，默认 quality=high，不自创字段。文件放当前项目约定的 _草稿 目录，正文与人读说明分开。先 validate；只有已授权生图才 submit。按返回 status 处理：hold 先问用户再 confirm，error 读原因后 retry，状态不明沿原 jobId 查询。结果在 GenDesk 人工验收。完整字段与恢复规则以本文为准。
