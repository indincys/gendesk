# GenDesk 命令行生图接入

适用版本：CLI / 应用 0.36.1，清单与文件工单 `version: 1`。本文是外部生图接入的唯一完整规范；README、AGENTS 和投单 skill 只保留入口与执行边界。写提示词不等于授权生图，只有用户要求生成或已有生成授权时才 submit。

GenDesk 接收 **UTF-8 正文文件 + 本地参考图 + 显式配对清单**。CLI 是零 npm 依赖的文件客户端，不提供 HTTP 服务；API Key、模型选择、收录、生成调度、重试、人工验收和成品交付由应用管理。外部工具不直接写 SQLite。

## 1. 版本、安装与连接能力

前置 Node.js ≥ 22。本机命令在 `~/.local/bin/gendesk`；macOS/Unix 从仓库安装或更新：

```bash
pnpm --dir /Users/indincys/Workspace/软件开发/GenDesk/代码 install:cli
gendesk --version
gendesk doctor
```

安装器核对 CLI、package.json 与应用配置版本，验证后发布 `~/.local/bin/gendesk` 命令入口与同目录的 `gendesk.mjs` 程序，分别原子替换。无扩展名入口用动态 import 加载明确的 ESM 程序，不依赖 Node 自动模块检测或所在目录的 package.json 类型；两文件保持在同一目录，不单独搬动。安装不改应用设置、不投单。应用升级不会自动更新这份独立 CLI，升级后须执行安装并核对。仓库内也可 `pnpm gendesk`，Windows 可 `node scripts/gendesk.mjs`。

`--version` 返回 JSON，含 `cliVersion`、`orderVersion`、`clientFeatures`，无需连接快照。`doctor` 另返回 `appVersion`、`features`、`enabled`、`taskThreshold` 和交接根。**clientFeatures 是客户端支持；features 是应用上次写出的能力，两者不可混用。** 版本号和工单格式版本也不是同一个概念。

| 应用连接能力 | 投递时的要求 |
| --- | --- |
| `generation-quality` | 所有新单均要求，防止默认 high 被旧应用忽略 |
| `ordered-references` | 同一条目有两张及以上参考图时要求 |
| `content-organization` | 顶层或条目填写 organization 时要求 |
| `intake-preflight` | validate / 新单投递调用 Rust 完整预检时要求 |
| `resumable-intake` | 所有新单投递均要求，确保收录有稳定身份检查点 |
| `background-intake` | macOS 上应用已退出时，`--open` 后台启动所需 |

连接快照 `~/GenDesk交接/连接.json` 由应用启动或保存收件设置时写出，包含连接配置和 validatorPath（当前应用可执行文件路径），**不代表应用在线**。缺少能力时更新并启动应用，不手改快照伪造支持。validate 使用已声明的预检程序；submit 还检查实际收件应用的安全恢复等能力。显式设置 GENDESK_APP_BIN 只能覆盖已知支持预检的程序路径，不能代替收件应用声明 resumable-intake。

交接根选择顺序：`--root` → `GENDESK_ROOT` → 连接快照 → `~/GenDesk交接`。root 是交接根，不是 `生图/收件`，也不是作品根。自定义根若不匹配连接快照，CLI 无法据此确认能力；先在应用设置中配置正确根并刷新快照。

## 2. 正文与参考图

- 一份非空 UTF-8 TXT = 一条提示词 = 一个任务 = 一张图。中文、英文、多段文字均可；不按段落、序号或 `====` 拆分。
- TXT 只放发给模型的正文，不放文件路径说明、SKU、写作分析或 Markdown 代码围栏。CLI 按原字节复制，Rust 收录时去掉首尾空白，正文中的“比例：3:4”不会被解析成参数。
- 接收层没有额外设定提示词字数上限；远端模型仍可能有自己的限制。没有单独的 negativePrompt、seed、n、model 或 API Key 输入字段，不自创参数。
- 参考图必须是存在、非空、可解码的本地文件；常规使用 JPG/PNG。URL、Base64 或对话里的图片标记不能代替文件路径；附件若有可访问路径即可使用，没有路径先取得实际文件，不编造路径。
- 单图用 `ref`；多图用 `refs` 有序数组，二选一。每项 1～16 张，不重复引用相同内容。多个条目可以共用参考图，CLI 按内容打包复用。
- 数组首张是 Image 1（主参考），第二张是 Image 2，依次类推。正文应说明各图角色；不要拼接触表、丢掉环境参考或依赖上一次请求记忆。多个附件不展开成多个任务。
- 参考图不用匹配输出尺寸，也不要求边长为 16 的倍数。应用对长边超过 2048 或文件超过 3 MiB 的参考图会尝试制作上传压缩副本；这不是接收文件大小上限，也不保证模型按原图像素读取。

## 3. 批量清单（推荐）

清单使用 UTF-8 JSON；相对路径以**清单所在目录**为基准，也支持绝对路径与 `~/`。显式配对每一条，不按两个目录的排序猜配对。以下示例需要将素材换成真实文件：

```json
{
  "version": 1,
  "note": "水杯厨房场景",
  "skill": "Codex场景提示词",
  "organization": {
    "product": "陶瓷水杯",
    "style": "奶油白款",
    "requirement": "厨房场景图",
    "source": "小红书晒单需求"
  },
  "defaults": { "ratio": "3:4", "format": "jpeg", "quality": "high" },
  "items": [
    {
      "name": "水杯晨光桌面",
      "promptFile": "提示词正文/水杯晨光.txt",
      "refs": ["商品实拍/水杯正面.jpg", "场景参考/厨房桌面.jpg"]
    },
    {
      "name": "水杯窗边竖幅",
      "promptFile": "提示词正文/水杯窗边.txt",
      "ref": "商品实拍/水杯正面.jpg",
      "ratio": "9:16"
    }
  ]
}
```

| 位置 | 字段与约束 |
| --- | --- |
| 顶层 | `version` 建议显式为数字 1，CLI 省略时补 1；非空 `items` 必填 |
| 顶层可选 | `jobId`、`note`、`skill`、`purpose`、`defaults`、`organization`、`refGroup`、`ephemeral` |
| 每个条目必填 | `name`、`promptFile`、`ref` 或 `refs` |
| 每个条目可选 | `organization`、`sku`、`style`，以及生成参数表里的各字段 |
| 字符串 | 路径、名字、SKU、归属、参数文本都用字符串；例如 SKU 写 `"55"` 而非数字 55 |
| `ephemeral` | 顶层布尔值；true 表示参考图仅作本批附件，不进入长期图库 |
| `refGroup` | 顶层非空字符串，指定参考图库分组，不是提示词分组或成品归属 |
| `purpose` | 整单级；普通生图省略，验收图确实用于后续转视频时写 `i2v` |

CLI 严格拒绝未知字段。对外统一使用本文中的字段名；不要把 Rust 内部快照字段（如 aspectRatio、referenceImageIds）放进 CLI 清单。

`name` 单内唯一，大小写及 Unicode 等价名字也不能重复；最长 180 个 UTF-8 字节，不得含控制字符或 `<>:"/\\|?*`，不得以点结尾或使用系统保留名。CLI 会去掉 name 首尾空白。它是语义名与工单内正文身份，不是最终文件路径；0.36.0 交付名按 `YYYY-MM-DD_内容名称_稳定身份.扩展名` 生成，目录和文件名会做安全规范化，原语义名保留在记录中，详见 [作品目录整理](作品目录整理.md)。

需要同一提示词的第二张图，增加一个不同 name 的条目；任务数始终等于条目数。

## 4. 内容归属与旧格式兼容

新任务推荐填写 `organization: {product, style, requirement, source}`。它决定按产品、款式、需求持续归档，来源只作追溯。产品、款式可留空，未知需求落到 `需求待补充`；应优先给用户能识别的固定需求名。同一需求续做沿用相同名称，不加入日期、续批、重做或随机编号；jobId 只管一次运行去重。

organization 可写顶层，也可写条目。**条目整对象覆盖顶层，不逐字段合并**；省略的归属属性在应用内按空字符串处理。产品、款式和需求非空时不得有首尾空白、路径或保留字符，最长各 180 UTF-8 字节；source 为追溯文本。没有 SKU 的任务只提供 organization，不编造商品编号。

旧清单不含 organization 时仍接受，条目 `sku`、`style` 必须是非空字符串，应用仅沿用明确字段作兼容归属，不从文件名猜产品。已有 Poster 商品映射需要 sku/style 时继续提供真实值，并与 organization 保持一致；organization.style 表示款式，不是任意视觉风格。作品根由应用设置决定，CLI 不指定或猜测成品目录。

## 5. 生成参数

参数可放在 defaults 或单条；**逐字段覆盖，未写的字段仍继承 defaults**。正文中描述比例、像素或“高清”不能代替参数。

| 字段 | 接收值 |
| --- | --- |
| `ratio` | `1:1`、`16:9`、`9:16`、`4:3`、`3:4`、`3:2`、`2:3`、`21:9` |
| `size` | `宽x高`（正整数，均为 16 的倍数），或 `auto` |
| `format` | `jpeg`、`png`；jpg 归一化为 jpeg；不接受 webp 作为输出格式 |
| `quality` | `auto`、`low`、`medium`、`high`、`xhigh`、`max`、`standard`、`hd`，缺省 high |
| `clearAiMetadata` | 布尔值，默认 true，本地输出处理开关 |
| `removeC2pa` | 布尔值，默认 true，本地输出处理开关 |

质量档位是否可用由远端模型决定；high 不是所有模型的最高档，此值与本地 JPEG 编码质量无关。CLI 接受的参数不等于所有模型都支持。

| 比例 | 缺少 size 时自动补的尺寸 |
| --- | --- |
| 1:1 | 1024x1024 |
| 3:4 | 1536x2048 |
| 4:3 | 2048x1536 |
| 2:3 | 1024x1536 |
| 3:2 | 1536x1024 |
| 9:16 | 1152x2048 |
| 16:9 | 2048x1152 |
| 21:9 | 2016x864 |

通常只填 ratio，让应用补配套 size；用户明确像素要求时再写 size，并自行保持比例一致。**defaults 同时写 ratio 和 size 时，条目改 ratio 必须一并更新 size，否则仍继承默认尺寸。** 当前后端不会拒绝比例与尺寸互相矛盾的组合，也不会替换你显式给定的 size。`1080x1920` 因 1080 不是 16 的倍数会拒单。请求尺寸不保证远端返回精确同像素，精确交付像素需验收后核对。

## 6. 单条入口与执行顺序

单条示例（产品、款式、需求和文件路径替换为实际值）：

```bash
gendesk validate --prompt /绝对路径/水杯晨光.txt --ref /绝对路径/水杯正面.jpg \
  --product 陶瓷水杯 --style 奶油白款 --requirement 厨房场景图 \
  --source 小红书晒单需求 --ratio 3:4 --format jpeg --quality high
gendesk submit --prompt /绝对路径/水杯晨光.txt --ref /绝对路径/水杯正面.jpg \
  --product 陶瓷水杯 --style 奶油白款 --requirement 厨房场景图 \
  --source 小红书晒单需求 --ratio 3:4 --format jpeg --quality high --open --wait 30
```

`--name` 省略时取正文文件名主干。单条只支持一个 `--ref`，多参考图改用清单；没有 `--refs` 参数。单条使用 --product、--requirement 或 --source 任一参数才创建 organization；非商品单可只给 --requirement。不填这三者则走旧 --sku + --style 兼容模式。

`--manifest` 不能与 --prompt、--ref、--quality、--product 等单条输入参数混用，修改内容应写回清单。可以与 --root、--job-id，以及 submit 的 --open、--wait 共用。

批量执行：

```bash
gendesk validate --manifest /绝对路径/场景任务.json
gendesk submit --manifest /绝对路径/场景任务.json --open --wait 30
gendesk status cli-返回的工单编号
```

validate 先检查文件、UTF-8 正文编码、字段类型、名字与配对，再调用应用可执行文件的 validate-intake 只读入口，复用 Rust 收录解析、参数归一化、归属校验和实际图片解码，返回 `validation: full`。预检不启动 GUI、不打开数据库、不建收件目录或缩略图、不调用生图。归一化后的参数在 preflight.items[].paramsJson / wireJson，参考图尺寸和 SHA-256 在 preflight.references；preflight.fingerprint 是本次内容身份，不是生成结果。原 order 仍为 CLI 请求字段。旧程序或缺少能力时明确报错，不静默降级为文件预检。应用关闭时，只要已有有效的新版程序路径也可预检。开发或便携环境可用 GENDESK_APP_BIN 指定已知支持该协议的程序。收录前仍重新核对实际输入，避免预检后文件变化；完整输入预检不承诺磁盘写入、远端模型/账号或服务端生成必定成功。

macOS 上 `--open` 会在 GenDesk 已退出时后台启动应用，运行中的实例直接收件。投单、收录和生成期间可以继续使用当前应用，验收时再从 Dock 或菜单栏打开 GenDesk。后台启动失败时返回 `openError`，已投递的工单保留。省略 `--open` 可离线排单，其他系统请先自行启动应用。

给 harness 的顺序：准备正文与清单 → validate → 在已有生成授权内 submit → 回读工单/批次回执 → 在 GenDesk 查看结果及人工验收。只写词时交付文件即可，不创建 READY 或提交。

## 7. 去重、回执与失败恢复

CLI 根据工单、正文和参考图内容生成稳定 jobId。同样输入重复调用复用原单，返回 reused=true；同 ID 不同内容报错，不覆盖。确实要额外生成一次且已有授权时，显式给新的 --job-id 或清单 jobId。**超时、收录失败或状态不明，先查原 ID，不自动换 ID 重投。**

CLI 复制文件到 `<交接根>/生图/收件/<jobId>/`，校验复制内容，最后写 READY.txt；不移动源文件、不建软链接。回读优先用机器回执，兼容文本回执，并查找 `_已收录` 中的工单。--wait 的单位为秒（0～3600），只等收录回执，不等生图完成。

| JSON 状态 | 含义 | 退出码 |
| --- | --- | --- |
| queued | 已投递，尚无收录回执 | 0 |
| staging | 无 READY，仍在写入或留下半份工单 | 2 |
| ingesting | 正在导入 | 0 |
| ingested | 已收录建批，不代表生成或验收完成 | 0 |
| hold | 超阈值待用户确认，尚未导入 | 4 |
| error | 收录失败，回执含已导入数量 | 5 |
| duplicate | ID 被台账占用，本次未收录 | 6 |
| not_found | 此交接根未找到工单 | 7 |
| client_error | 输入或配置错误；收件关闭也返回此状态 | 2；收件关闭为 8 |
| timedOut=true | 附加标志，等待超时，工单仍在 | 3 |

超过应用阈值（默认 100 张）时先显示条数和配对，用户确认后在应用放行；0.36.0 也可在用户明确同意后向工单目录写 `确认.txt`。已有生成授权不等于可以绕过这道阈值确认，CLI 没有绕过开关。

0.36.1 新工单持久保存原 jobId、内容指纹、提示词 ID、参考图 ID 与导入阶段。每阶段业务写入和身份检查点同事务提交，最终建批和收录完成台账也在同事务内；应用内对原工单“重试”只补未完成部分，保留已有身份，不删台账再整单导入。快速重复点击、进程重启后的重试不会多建批次。CLI 重复 submit 仍只复用和查询原单，不会暗中触发失败重试。

error 时先读回执，在 GenDesk 设置页对原工单重试。已经导入过内容后，正文、归属、参数、参考图内容及原包内参考路径须保持一致；改变内容、删除已导入记录或缺失原图会停止恢复，不能靠换 ID 绕过。尚未导入任何业务记录的工单可以修正错误后重试，条目数增加仍受阈值约束。确实要改内容重新生成时先核对原单已完成部分，再在用户授权下新建任务，不自动重跑成功项。

**旧版本留下的部分导入或 running 工单若没有身份检查点，会明确拒绝盲目重放**，保留台账与回执供核对；不从名字或数量猜已导入对象。旧错误单若明确零导入，可修正后沿原 ID 重试。staging 时先确认没有客户端仍在写，保留并处理半份工单，不直接换 ID 重发。应用内人工验收后才发 UID 和交付；CLI 不自动验收。

## 8. 手动文件工单（无 CLI 的兼容入口）

优先使用 CLI；只有调用环境不能运行它且用户已授权生成时才手动打包。先从连接快照发现交接根，不固定写默认目录。目录结构：

```text
<交接根>/生图/收件/<全局唯一jobId>/
├── 工单.json
├── prompts/<name>.txt
├── refs/<参考图文件>
└── READY.txt
```

与 CLI 清单的差异：工单 version=1 必填；没有 promptFile 字段，正文固定为 prompts/<name>.txt；ref/refs 必须是包内相对路径，不能是绝对路径或包含 ..。复制真实参考图，不移动、不建软链接；prompts 下 TXT 与 items 严格一一对应。工单填写显式稳定 jobId，READY.txt 最后写。不要用分钟级日期或随机目录名代替失败恢复策略。

手动包不包含 CLI 的客户端内容哈希文件，不能再用 CLI submit 覆盖或复用；status 仍可查询原 jobId。应用不接受旧 `提示词.txt + images/` 生图包；文本回执兼容不等于旧包格式兼容。

## 9. 给提示词 Codex 的简短约定

> 按 GenDesk 0.36.1 接收契约交付：每张图一份 UTF-8 纯正文 TXT，另写 version=1 的 JSON 清单。逐项指定 name、promptFile 和 ref 或有序 refs；多图在正文说明 Image 1、Image 2 的用途。新任务填写 organization 的产品、款式、固定需求和来源，没有 SKU 不编造编号。ratio/size/format/quality 写参数，默认 quality=high，不自创字段。文件放当前项目约定的 _草稿 目录，正文与人读说明分开。先 validate；只有已授权生图才 submit。回读收录回执，超时沿原 jobId 查询，结果在 GenDesk 人工验收。完整字段与恢复规则以本文为准。
