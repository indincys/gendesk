## 0. 决策背景

GenDesk 当前把「生成」和「素材/任务单管理」两件事都揽在身上，与 `自动发布`
（`/Users/indincys/Documents/自动发布`）的六库 + 任务单生成器正在重复建设。

**定案**：GenDesk 只负责「把图生出来、验收、按确定的名字交付」；SKU 归属、素材库、
任务单全部由 `自动发布` 承担。两个软件之间的契约是**交付目录 + manifest**，不是共享数据库。

图片的身份从此**写在文件名上**：`W-王一博-55-正面-hu72.jpg`

| 段 | 含义 | 谁给的 |
| --- | --- | --- |
| `W-王一博-55-正面` | 语义名（含 SKU 数字缩写 `55`） | skill，GenDesk 一个字符都不改 |
| `hu72` | 4 位随机 UID，全局唯一 | GenDesk，验收通过那一刻发放 |

## W2 · 命名与发号台账

### 数据结构（0045）

**新表 `issued_names` —— 只增不删的发号台账**

```sql
CREATE TABLE issued_names (
  name      TEXT PRIMARY KEY,   -- 完整文件名主干：W-王一博-55-正面-hu72
  uid       TEXT NOT NULL,      -- hu72
  work_id   INTEGER,            -- 无外键，允许孤儿
  issued_at INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_issued_names_uid ON issued_names(uid);
```

**不设外键、不随作品删除而消失。** 作品是本仓库唯一「删除即真删行」的实体；作品一删，
uid 就失忆了，而那个文件很可能早已交付到 `自动发布` 那边。这张表只回答一个问题：
「这个名字/UID 历史上发出去过没有」。设计理由同 `work_exports`（0018）。

**`accepted_works` 加四列快照**

```sql
ALTER TABLE accepted_works ADD COLUMN item_name TEXT NOT NULL DEFAULT '';  -- W-王一博-55-正面
ALTER TABLE accepted_works ADD COLUMN uid       TEXT NOT NULL DEFAULT '';  -- hu72
ALTER TABLE accepted_works ADD COLUMN sku_code  TEXT NOT NULL DEFAULT '';  -- 55
ALTER TABLE accepted_works ADD COLUMN style     TEXT NOT NULL DEFAULT '';  -- 王一博
```

理由与 0027 给 `prompt_code`/`group_name` 存快照完全一致：**下游存快照**。
提示词是消耗品，批次跑完即删；而人隔几天才回来验收是常态。不冗余的话，manifest 到那时
就写不出 SKU 了。

### 发号规则

| 规则 | 内容 |
| --- | --- |
| R1 | 发号与写作品**同一个事务**。直接 `INSERT INTO issued_names`，撞 UNIQUE 就重摇（上限 8 次后报错）。**禁止**「先 SELECT 查重再 INSERT」——查与插之间就是重名窗口 |
| R2 | `reexport_work` **复用原 uid**，绝不重摇。uid 是作品的属性，不是导出动作的属性 |
| R3 | uid **不回收**。撤销验收、作品进废纸篓、清空废纸篓都不还号（同号池「编号不回收」） |
| R4 | UID 字符集 `[a-z0-9]`，长度 4；**全局唯一**（不按前缀分域），这样 `自动发布` 可以只存 uid 当主键 |

### 验收标准

- [ ] 单测：同一 `item_name` 连续验收两次 → 两个不同 uid，`issued_names` 两行
- [ ] 单测：模拟 UID 生成器固定返回同一个值 → 第二次插入触发重摇路径，重摇耗尽后返回可读错误
- [ ] 单测：作品被删（`trash` → `purge`）后 `issued_names` 行数不变
- [ ] 单测：`reexport_work` 前后 `accepted_works.uid` 不变、不新增 `issued_names` 行
- [ ] 集成测试：批次退休（`retire_resolved_batches`）删掉提示词后，
      `accepted_works` 的 `sku_code`/`style`/`item_name` 仍可读出正确值

## W3 · 工单格式 v2（skill 产出 + intake 收录）

### 目录形状

```
投单-260804-1530/
├── 工单.json                       ← 全部元信息
├── refs/
│   ├── 王一博-正面.jpg
│   └── 王一博-侧面.jpg
├── prompts/
│   ├── W-王一博-55-正面.txt         ← 文件名 = 未来的图片名主干；内容 = 纯正文
│   └── W-王一博-55-侧面.txt
└── READY.txt                       ← 最后写，没有它一个字节都不碰
```

### `工单.json`

```json
{
  "version": 1,
  "purpose": "i2v",
  "defaults": { "ratio": "9:16", "size": "1080x1920", "format": "jpeg" },
  "items": [
    {
      "name": "W-王一博-55-正面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-正面.jpg"
    },
    {
      "name": "W-王一博-55-侧面",
      "sku": "55",
      "style": "王一博",
      "ref": "refs/王一博-侧面.jpg",
      "ratio": "3:4",
      "size": "1080x1440"
    }
  ]
}
```

### 相对旧格式的变化

| 旧 | 新 |
| --- | --- |
| `提示词.txt` 单文件 + 组头键（`参考图:`/`比例:`/`尺寸:`/`格式:`/`抽卡:`/`用途:`） | `工单.json` + `prompts/{name}.txt` 一条一文件 |
| 组头键**位置绑定**（只在该组第一条正文之前生效） | 规则整个消失——正文文件里没有键，不可能被误吃 |
| `参考图:` 是**组级**挂靠 | `ref` 是**条目级**，每条必填 |
| 参数按 `(参数, 抽卡)` 分桶成多个批次 | 参数跟着任务行走，**不再决定 run 的切分** |
| 组名 → `prompt_groups` | 无组概念；`name` 即身份 |

### 校验（全部在命令边界强制，失败即拒单）

- [ ] `items[].name` 非空、文件系统安全、**单内唯一**
- [ ] `items[].ref` 指向的文件在包内存在 —— **挂靠不猜**，缺失直接拒单
- [ ] `prompts/{name}.txt` 与 `items[].name` **一一对应**，多一个少一个都拒
- [ ] `sku` / `style` 非空
- [ ] `ratio` 与 `size` **必须成对生效**（实测：单发 `aspectRatio` 回来整批是 1024×1024
      正方形；单发 `size` 且边长非 16 倍数则整批 400）。取值单点仍是 `provider::RATIO_SIZES`
- [ ] **归一化只改拼法不改取值**：`jpg → jpeg` 是拼法；边长非 16 倍数是取值 → **拒单**
- [ ] 超阈值（默认 100 张）→ 转 `hold`，**什么都不导入** + 应用内确认卡
- [ ] `job_id` 去重记账在**动手之前**（重复收录 = 重复花钱）

### 失败回执

沿用现规则：**必须写明已导入到哪一步**。这串动作没有一步能整体回滚，
谎称「没有导入任何东西」会让人点重试拿到第二份提示词。

### 验收标准

- [ ] 新增 intake 集成测试：正常单 → 任务数 = `items.length`，每条任务的参考图与
      `工单.json` 一致
- [ ] 新增 intake 集成测试：`ref` 指向不存在文件 → 拒单，**零导入**
- [ ] 新增 intake 集成测试：`prompts/` 与 `items` 数量不匹配 → 拒单，零导入
- [ ] 新增 intake 集成测试：`format: "jpg"` → 归一化为 `jpeg` 并通过；`size: "1000x1500"`
      → 拒单（非 16 倍数）
- [ ] 提示词正文进 `prompt_text_snapshot` 时**逐字符等于** txt 文件内容（无元信息混入）
- [ ] `.claude/skills/gendesk-intake/` 两份文档与 `docs/提示词skill标准产出规范.md` 同步改写

## W4 · 用途载体与 v2v 解耦

### 问题

「哪些图要进视频流水线」目前绑在 `prompt_group` 上——作品库靠
`tag_bindings.entity_type='prompt_group'` 判 `is_i2v`（`commands/works.rs:62`）。
无组之后这个载体消失，v2v 入队判定会当场哑掉。

同理 v2v 交接目录按 `g{group_id}` 切，skill 按这个结构读写。

### 改法

| 项 | 旧 | 新 |
| --- | --- | --- |
| 用途载体 | `tag_bindings(entity_type='prompt_group')` | `工单.json` 的 `purpose`（整单级），落到任务行 / 作品行 |
| `is_i2v` 判定 | JOIN `tag_bindings` | 读作品自己的 `purpose` 快照列 |
| 交接目录切分 | `g{group_id}`（对同一组恒定） | `j{job_id}`（对同一投单恒定） |

`accepted_works` 再加一列 `purpose TEXT NOT NULL DEFAULT ''`（与 W2 的四列同一次迁移）。

### 不变的部分（照旧，别顺手改）

- 交接目录**只监听「已改写」**（连「待改写」一起监听会形成物化 → 收录 → 物化的自激循环）
- **skill 边界**：只改写提示词，不调 dreamina
- 幽灵判定、通道计算、额度切窗全部不动

### 验收标准

- [ ] 单测：`purpose = "i2v"` 的工单，其图验收通过后**自动入 v2v 待发队列**
- [ ] 单测：`purpose` 非 `i2v` 时不入队
- [ ] 单测：同一 `job_id` 两次物化交接目录，目录名恒定
- [ ] v2v 现有测试全部仍绿（尤其通道相关：`count_in_flight_on` / `free_slots` /
      `drain_queue` / autofill **一律按通道算**）

## W5 · 批次退到幕后

### 改法

**保留** `batches` 作为内部运行单元（暂停/取消/重试/进度汇总/退休清理都挂在它上面），
**去掉**它作为人的浏览轴与文件系统命名的角色。

| 位置 | 旧 | 新 |
| --- | --- | --- |
| 切分粒度 | 按 `(参数, 抽卡)` 分桶，一单可能多批 | **一次工单 = 一个 run** |
| 输出目录 | `outputs/{batch_id}/{分组名}/` | 交付目录（见 W6），不再用 batch_id 命名 |
| 验收页分节 | 日 → 任务簇 | **按投单分节**（`_shared/timeline.ts` 改分段键） |
| 任务页 | 全部在制任务 | 不变 |

### 验收页虚拟化的既有约束（改分节时必须守住）

- `estimateSize` 必须是真值，**不许挂 `measureElement`**（逐行 `getBoundingClientRect`
  是滚动时的强制同步布局）
- 新分组头一律**定高**，TS 常量与 CSS 是一对，改一处必须改另一处
- 容器宽度只能取 `ResizeObserver` 的 `contentRect.width`，**不能拿 `clientWidth` 兜底**
- 齐行修饰必须排在基类之后（`.rjimg` 另把 `width:100%` 显式写死）

### 验收标准

- [ ] 单测：一份含 3 种不同参数的工单 → **恰好 1 个批次**
- [ ] `styles/classnames.test.ts` 绿（新分组头 class 有定义且被用到）
- [ ] `features/_shared/timeline.ts` 单测覆盖新分段键
- [ ] 500 任务真机：验收页滚动无相邻行重叠、无卡顿

### `manifest.jsonl`（一行一图）


### 写盘协议

| 规则 | 内容 |
| --- | --- |
| D1 | 整批拷完 → 写 `manifest.jsonl` → **最后**写 `READY.txt`。对方没看到 READY 就一个字节都不碰 |
| D2 | 拷贝**先整批做完再动库**，任一张失败就整个报错、一行库都不写（沿用 `accept_tasks` 现有顺序——拷贝无法回滚，单事务反而更糟） |
| D3 | 交付即**交出所有权**。文件被 `自动发布` 搬走后 `accepted_works.image_path` 允许悬空，UI 走已有的 `file_exists` 懒检测；救回路径是 `reexport_work`（从 `results/{task_id}` 快照重出，复用原 uid） |
| D4 | 旧落点 `outputs/{批次}/{分组}/` **停止写入**。视频交付 `outputs/视频/` 不动 |

## 4. 已知陷阱速查（实施时逐条对照）

1. **发号不能「先查再插」** —— 查与插之间就是重名窗口。同 `claim_ready` 那三处并发窗口，
   代价都是钱。
2. **SKU 元数据必须快照到 `accepted_works`** —— 提示词是消耗品，批次退休即删；
   隔天验收时上游已经没了。
3. **`issued_names` 不能随作品删除而消失** —— 文件可能已经交付出去了。
4. **`ratio` 与 `size` 两个字段都要发** —— 单发任何一个都会得到错误画幅。
5. **归一化只改拼法不改取值** —— 静默改值正是「我明明写了 9:16 却不生效」的成因。
6. **迁移 forward-only** —— 废弃列保留不读不写；改动建议先在真实库副本上跑
   `foreign_key_check` + `integrity_check`。
7. **`tag_bindings` 是无外键的多态表** —— W4 拆掉用途标签时必须手动清理残留绑定，
   否则分组 id 被复用时旧绑定会把用途安到无关的组头上。
8. **dev 与打包应用共用同一个 `app_data_dir`** —— 本方案有 2 次迁移（0044/0045），
   跑过 `pnpm tauri dev` 之后 `/Applications` 里的旧包将无法启动（`VersionMissing`，
   这是保护不是故障）。
9. **`pnpm check` 第 8 步用 `git diff --exit-code` 校验 bindings 同步** ——
   改完命令必须 `cargo test --lib export_bindings` 重生成后**先 `git add` 再跑门禁**。

- 一个工作项 = 一个分支 = 实现 + 测试 + 门禁全绿 + 审查通过 = 一次 merge。main 受保护。
